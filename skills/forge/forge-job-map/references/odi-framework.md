# ODI (Outcome-Driven Innovation) Framework Reference

Source: Tony Ulwick, "What Customers Want" + Workshop X defense adaptation

## Opportunity Algorithm

```
Opportunity Score = Importance + max(Importance - Satisfaction, 0)

Score range: 0-10 (when using 1-5 scale for Imp and Sat)

Interpretation:
  ≥ 8.0  HIGHLY UNDERSERVED — top innovation target
  6.0-7.9  UNDERSERVED — strong opportunity
  4.0-5.9  SERVED — adequate, maintain
  ≤ 3.9  OVERSERVED — cost reduction candidate
```

## Outcome Statement Rules

1. Always start with "Minimize" or "Maximize" (95% should be Minimize)
2. Include a measurable metric (time, likelihood, number, effort)
3. Include context (when, where, under what conditions)
4. Must be solution-neutral (no product/technology names)
5. Must be testable (can you measure it?)

### Template
```
"Minimize the [metric: time/likelihood/number/effort] it takes to
 [action related to job step] [contextual clarifier]"
```

### Examples by Job Step

| Step | Example Outcome |
|------|----------------|
| 1. DEFINE | Minimize the time to determine which area needs monitoring |
| 2. LOCATE | Minimize the effort to find all required equipment |
| 3. PREPARE | Minimize the number of people needed for setup |
| 4. CONFIRM | Minimize the time to verify system is operational |
| 5. EXECUTE | Minimize the likelihood of missing a real target |
| 6. MONITOR | Minimize the effort to check system health during operation |
| 7. MODIFY | Minimize the time to adjust detection parameters |
| 8. CONCLUDE | Minimize the maintenance required between deployments |

## 5 Growth Strategies (from Opportunity Landscape)

| Strategy | When | Action |
|----------|------|--------|
| **Differentiated** | Many outcomes underserved | Target top underserved, charge premium |
| **Dominant** | Can serve ALL outcomes | Comprehensive solution, market leader |
| **Discrete** | Many outcomes overserved | Strip features, lower cost |
| **Sustaining** | Most outcomes adequately served | Incremental improvement |
| **Disruptive** | New way to get entire job done | Platform play, redefine market |

## Defense-Specific Adaptations

| Standard ODI | Defense Adaptation |
|-------------|-------------------|
| 180+ survey respondents | 15-30 users (structured interviews) |
| Online survey | Face-to-face, on-site observation |
| Consumer language | Military operational language |
| Open market | Procurement-gated market |
| Buyer = User | Buyer (procurement) ≠ User (operator) |
| Annual refresh | Bi-annual (military jobs stable) |

## Customer Segmentation by Outcomes

NOT by demographics. By unmet outcome clusters:

```
Segment A: "Rain operators" — care most about weather resilience
Segment B: "Rapid deployers" — care most about setup speed
Segment C: "Night shifters" — care most about low-light performance
```

Each segment = different product configuration or ACH priority.
